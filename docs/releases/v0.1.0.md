# Halquen v0.1.0

Halquen v0.1.0 is the first public Linux pre-release of the local-first authority and execution
layer for AI agents.

## Highlights

- Tauri v2 and React desktop client for chat, activity, memory, AI, diagnostics, settings, and
  security administration.
- Versioned JSON protocol over a private Unix socket shared by the desktop and CLI.
- Deterministic local chat routing, evidence-backed memory revisions, feedback-gated response
  reuse, and optional OpenAI-compatible providers.
- Exact policy decisions, single-use confirmations, persistent scoped allow/deny permissions,
  resource classification, and durable execution audit records.
- Daemon-brokered CLI agents with strict bounded JSON, typed identity/session scope, resource
  limits, and a fail-closed Bubblewrap backend.
- Explicit real execution limited to daemon-registered `system.open_app` applications. Dry-run
  remains the default and the executor never invokes a shell.

## Install

Download `SHA256SUMS` and the assets for this release, then verify them:

```bash
sha256sum -c SHA256SUMS
```

The portable archive contains `halquen`, `halquen-daemon`, `README.md`, and `LICENSE`:

```bash
tar -xzf halquen-v0.1.0-x86_64-unknown-linux-gnu.tar.gz
install -Dm755 halquen-v0.1.0-x86_64-unknown-linux-gnu/halquen ~/.local/bin/halquen
install -Dm755 halquen-v0.1.0-x86_64-unknown-linux-gnu/halquen-daemon ~/.local/bin/halquen-daemon
halquen-daemon
```

Install a separately published desktop bundle if desired. The desktop and CLI both require the
daemon to be running; no systemd unit or autostart entry is installed by this release.

This pre-release includes Debian and RPM desktop bundles. An AppImage is not included because the
upstream `linuxdeploy` tool bundled by Tauri could not process Fedora 44 system libraries that use
ELF RELR sections; no unsafe tool substitution was used to bypass that packaging failure.

## Security model

- AI, agent, plugin, and external content are proposal data, never execution authority.
- Policy creates exact action-bound authorization after immutable hard-deny and scoped permission
  checks.
- Provider credentials are stored only in the operating-system keyring; there is no plaintext
  fallback.
- Real application launch uses a registered canonical executable and fixed arguments, revalidates
  identity immediately before direct spawn, and does not use a shell.
- Brokered agents cannot supply action context or executable paths; all proposals return to daemon
  policy.

## Known limitations

- Linux and single-user local deployment are the supported v0.1.0 environment.
- Executable identity verification is path-based and narrows, but does not eliminate, the
  verification-to-spawn race.
- Bubblewrap and `prlimit` must be available for sandboxed agents. Aggregate `temp_bytes` is
  stored but is not yet enforced as a tmpfs quota.
- Registered applications are trusted, unsandboxed same-user programs.
- The Unix socket relies on user-owned private runtime-directory and socket permissions; there is
  no additional role separation between processes running under the same UID.
- The project has no automatic updater, installer-managed daemon service, or background provider
  polling.
- The sole accepted vulnerability/unsoundness advisory is the explicitly documented upstream
  `RUSTSEC-2024-0429` issue in the GTK/GLib dependency chain. The audit also reports allow-listed
  unmaintained transitive GTK/Tauri, Unicode, and proc-macro dependencies, plus a yanked
  `chacha20 0.10.1` lockfile entry with no active dependency path; new vulnerability or unsoundness
  advisories remain a release blocker.

## Verification

The release gate runs locked Rust formatting, check, tests, Clippy, frontend typecheck/tests/build,
dependency audit and policy checks, safe dry-run/real/deny smoke tests, Tauri packaging, checksum
verification, and final Git/GitHub readback.
